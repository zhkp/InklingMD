## 1. 版本定位

本版本交付 **Quick Open（键盘优先的文件快速打开）**，把「打开文件」这条最高频路径从「鼠标找侧边栏 → 逐层展开目录 → 点文件」变成 `Ctrl/Cmd+P` → 输入几个字符 → 回车。

Epic #222 拆成两个子项，本版本一并交付：

| 子项 | issue | PR | 内容 |
|---|---|---|---|
| 1/2 | #227 | #240 | Rust 侧统一工作区忽略规则 + 新增工作区文件索引命令（**不含 UI**） |
| 2/2 | #228 | #242 | 前端索引缓存层 + 打分排序 + 面板 UI + 快捷键/模态互斥 |
| 计划收口 | #222 §7.1 第 3 项 | #243 | 补「目录符号链接不被跟随」的断言（只加测试，不改实现） |

设计上刻意让「索引能力」与「面板 UI」分两次落地：Rust 命令只提供「给我这个工作区里所有 markdown 文件」这一件事，前端的所有排序/过滤策略都不依赖它的内部实现；子项二的开发计划里明确写了「不得引入前端代次计数器」（原因见 §2.3）。

## 2. 子项 1/2：统一 ignore 规则与工作区文件索引（#227，PR #240）

### 2.1 背景与根因

issue #227 的前提成立，但实测发现三处它没写到的实情：

1. **忽略黑名单实际有三份**，不是两份：`src/lib/searchIgnore.ts`（14 项）、`src/rust/search.rs::IGNORED_SEARCH_DIRS`（同 14 项、顺序不同）、`commands/mod.rs::IGNORED_DIR_NAMES`（5 项子集，文件树用），靠注释手工同步。
2. **前端那份是死代码**：`isIgnoredSearchDir` 全仓只被自己的测试 import，生产代码零调用。
3. **`.gitignore` 完全不生效**：只认硬编码目录名，`venv/`、`.venv/`、`vendor/`、`Pods/`、`__pycache__/` 里的 `.md` 会被全局搜索扫到——索引建起来后该问题会被放大。

### 2.2 忽略规则的唯一真值源（`commands/ignore_rules.rs`）

**忽略来源穷举（不多不少）**：

| 来源 | 说明 |
|---|---|
| 默认目录黑名单 `DEFAULT_IGNORED_DIRS` | 沿用原有 14 项，集合与语义完全不变，不新增硬编码目录 |
| 工作区内的 `.gitignore`（含嵌套子目录） | 新增生效：`venv/`、`vendor/`、`Pods/`、`__pycache__/` 由它解决，这才是根因修复 |
| 点号前缀隐藏项 | 名称以 `.` 开头，与文件树判定同语义、跨平台一致 |

**明确不启用**：`.ignore`（fd / ag 等工具的约定文件）、git 全局排除、`.git/info/exclude`、祖先目录的 `.gitignore`。

两处实现细节值得留意：

- `hidden(false)` + 在 `filter_entry` 里自行按点号前缀判定——**不复用 ignore crate 的「Windows 隐藏属性」判定**，否则带隐藏属性的普通文件会被连带过滤，与文件树语义不一致（有 `#[cfg(windows)]` + `attrib +h` 用例锁定）。
- `.ignore(false)` **显式关闭**：旧实现也不读它，但默认值将来可能变化，故把「不生效」写成契约 + 用例锁定，而不是留给默认行为。

删除 `src/lib/searchIgnore.ts` 与其测试后，Rust 侧成为唯一真值源。（9 个点号条目在三个消费方本来就不可达——`list_dir_shallow` 与 `filter_entry` 都先做点号判定；保留它们只为让清单与历史 14 项逐项一致，注释已如实写明「不要以为它们当前在起作用」。）

### 2.3 `list_workspace_files` 命令（`commands/file_index.rs`）

```rust
#[tauri::command]
pub async fn list_workspace_files(root: String) -> Result<WorkspaceFileList, String>
```

- **代次由 Rust 侧分配**（`next_generation(&INDEX_GENERATION)`，`fetch_add(1) + 1`），命令**不接受**前端代次。评审第二轮推演指出：`fetch_max` + 各 webview 独立计数器 = 「先到的窗口永久胜出、后开的窗口被永久饿死」，与注释声称的「后发起者胜出」相反——**裁决为改机制而不是改注释**：Rust 侧分配对任意并发请求严格单调，「最新请求胜出」跨窗口自然成立，前端因此**零状态**（不再需要、也不应维护计数器）。
- `INDEX_GENERATION` **独立于** `SEARCH_GENERATION`：两者共用一个计数器会让「打开 Quick Open」把在途的全局搜索取消掉，属可观察的行为耦合——复用的是**机制**（代次 + 检查点提前退出），不是变量。
- `MAX_INDEX_FILES = 50_000` + `truncated` 标记；结果按路径字节序升序（与历史 `files.sort()` 一致，保证分片合并顺序确定）；路径为**平台原生分隔符**（与 `list_dir`、搜索结果一致），调用方展示前自行归一化。
- `root` 为**文件**时不做特判：交给 `walk_markdown_files` 产出该文件自身，markdown 判定与 UTF-8 路径判定同一处，避免两份逻辑漂移。
- 六处登记：`commands/mod.rs`、`lib.rs` 的 `invoke_handler`、`permissions/app-commands.toml`、`capabilities/default.json`、`tests/unit/capabilities.test.ts`（14 → 15 项）、前端封装。

前端封装与 `mockFs` 分支**不在本 PR** 交付：实施时发现它们在 #227 内没有调用方（调用方是子项二的面板），会违反「杜绝死代码」，也与 #227「非目标：不做 UI」冲突——移入 #242 随 UI 及其 E2E 一起交付。

### 2.4 行为变化（已裁决口径）

| # | 变化 | 口径 |
|---|---|---|
| 1 | 文件树忽略目录 5 项 → 统一 14 项 | **实际新隐藏的只有 `coverage/`**（`out` 原就在旧清单里；9 个点号条目原就被点号判定覆盖）。文件仍可通过「打开文件」对话框直接打开 |
| 2 | 全局搜索新增 `.gitignore` 过滤 | #227 的目标行为，结果是**减少**（用户预期内） |
| 3 | 隐藏项语义 = 点号前缀 | **不含** Windows 隐藏属性，与文件树一致 |
| 4 | `.ignore` 不生效 | 与旧行为一致，现为显式关闭 + 用例锁定 |
| 5 | 索引代次由 Rust 侧分配 | 严格单调；前端不传代次 |

### 2.5 性能对照（第一轮评审 P3-9 要求）

合成工作区（`d000…/f000.md` + 非 md 噪声 + `node_modules/` 500 + 被 `.gitignore` 排除的 500），**交替顺序**各跑 5 轮取中位数：

| 规模 | 旧实现（手写递归） | 新实现 | 倍数 |
|---|---|---|---|
| 1 万文件 | 1.543 s（10,500 条） | **52 ms**（10,000 条） | ~29× |
| 5 万文件 | 7.536 s（50,500 条） | **257 ms**（50,000 条） | ~29× |

1 万 → 5 万（5×）两侧耗时 4.88× / 4.94×，**线性**。差异来源：旧实现每个条目多调 `is_dir()` / `is_file()`（Windows 上是额外 stat），且每个文件名做一次 `to_lowercase()` 分配；新实现基于 dirent 的 `file_type`。

口径声明：Windows 单机、warm cache、合成树；**不进 CI 门禁**（绝对耗时在共享 runner 上不可分辨），仅作后续基线。

## 3. 子项 2/2：Quick Open 面板（#228，PR #242）

### 3.1 分层


### 3.2 索引缓存层（`src/lib/workspaceIndex.ts`）

- **懒构建 + `INDEX_TTL_MS = 30_000` + stale-while-revalidate**：TTL 过期**先返回旧结果**再后台重建（不出现空面板等待）。
- **`invalidateEpoch` 世代号（评审 P2-1，阻塞项）**：失效拦不住「在途请求落定后写回」——失效后旧清单会以新 `builtAt` 被当成新鲜数据，TTL 内一直读到重命名前的路径。修法是发起前捕获 epoch、落定时比对；**并多做一步**：把结果标记 `stale` + 立刻补一次重建（只挡住回写的话，调用方仍会拿到 `stale=false` 的旧清单并渲染）。
- **递归消费 `refresh` 链（TomGoh 复审 P2，真 bug）**：面板原先只对 `snapshot.refresh` 挂一层 `.then`，`fresh.refresh` 被丢弃 → 只要**一次**失效落在「TTL 后台重建在途」窗口里，面板就会渲染中间版本且永远等不到最终数据。改为可自引用的 `consume` 递归跟进到 `refresh === null`。
- **两条 mint 路径统一兜底（评审 P3 + 自查）**：epoch 路径与 TTL 路径产出的 `refresh` 都可能没有消费方（面板在「已取消」路径早退），补重建失败会冒出 `unhandledRejection`。两条路径统一到 `startBackgroundRebuild()`，在 **mint 处**兜底——模块自己保证不产出孤儿 promise。
- **单文件模式 relPath 基准（TomGoh 复审 P2，真 bug）**：`relativeToRoot` 对基准外路径返回 basename，而单文件模式的 `rootPath` 只是其中一个文件的父目录 → `/a/report.md` 与 `/b/report.md` 无法区分、搜 `b/report` 搜不到。新增 `commonParentDir()` 取最深共同父目录（求不出返回 null → 退回完整路径）。未采用「直接用完整路径」：那样 `depthOf` 的绝对嵌套深度会进打分，而 2/级 相对 10/位 的 recency 并不可忽略，可能压过更近打开的文件。
- **落定回调的判断顺序（评审 P3-①）**：「在途失效」判断排在「工作区已切走」之前时，`build()` 开头无条件把 `latestRoot` 置为该 root，会让当前工作区的结果被误判为「已切走」而不写缓存。两判断对调，并按复审场景 D 新增回归用例（修前 `roots=['/w1','/w2','/w1']`）。
- `fileTree.ts` 的 `refreshTree` 成功后失效缓存——重命名/删除/另存为转正都以它为出口，**失效点只有一处**。30s TTL 内切回旧工作区会命中它自己的旧缓存，是既定语义（正确性来自 `cache.root === rootPath` 键比对），注释已写明这是排查陷阱。

### 3.3 打分排序纯函数（`src/lib/quickOpenScore.ts`）

```
score = 已打开(+1000) + 最近打开(0~100，步长 10) + 匹配档位分(0~100) - 深度 × 2
```

六档匹配取**最高不叠加**：`basename` 精确 100 / 前缀 80 / 子串 60 ＞ 路径子串 50 ＞ 子序列 20~50。

排序键：`score ↓ → relPath(小写) ↑ → 绝对路径 ↑`，全部 **code-unit 比较（禁用 `localeCompare`）**，保证跨平台 / 跨 locale 确定。

**与计划书的偏差**：计划书写深度惩罚为 `+ depth * 2`，实现为 **`- depth * 2`**。公式是「分高者靠前」，惩罚必须为减，否则越深越靠前，与「优先根附近文件」相反（代码注释已标注该修正）。

### 3.4 面板 UI 与可访问性

- **渲染上限 `MAX_RENDERED_RESULTS = 200`** + 底部提示「仅显示前 200 条，继续输入以缩小范围」，**不做虚拟滚动**：上限已把 DOM 封顶 200 行，为被封顶的列表引入虚拟化等于无实际作用的代码；且虚拟滚动 + 键盘高亮 + `scrollIntoView` 是本项目已知易 flaky 区域。组件内留注释：若未来提高上限需同步引入虚拟滚动。
- **a11y 采用 WAI-ARIA combobox 模式**：焦点**始终留在输入框**，用 `aria-activedescendant` 指向当前项；补 `aria-label`（否则屏幕阅读器只念「组合框」）、`aria-expanded` / `aria-controls` / `aria-autocomplete`；面板声明 `aria-modal="true"` 故补**焦点陷阱**（Tab / Shift+Tab 双向环绕）让该语义名副其实。**未复用 `useMenuA11y`**：该 hook 会把 DOM 焦点移到 `[role="menuitem"]`，夺走输入框焦点、打断连续输入，与同一条目要求的 `aria-activedescendant` 互斥。
- **IME 组字守卫**：组字期间（`e.nativeEvent.isComposing`）的 Enter / 方向键不是命令——拼音按 Enter 确认候选原本会同时打开文件并关掉面板。同类扩展到面板的 Esc 关闭监听（组字期间 Esc 通常是取消候选）。用例含正向对照（组字结束后同一按键仍生效），防守卫过宽。
- **失败反馈**：打开失败在面板内以 `role="alert"` 提示且**不隐藏列表**（便于改选）——`fileOpenErrors` 原先只在侧边栏渲染，而失败多半是文件已删除、根本不在文件树里。
- 候选集构建与排序拆成两个 memo：纯打字不再重建候选对象（含 5,000 次路径归一化）；最近文件序位改用 Map，去掉每个候选一次线性查找。`scoreCandidate(candidate, matchScore)` 直接收已算好的档位分，每次按键的 `matchScoreOf` 调用减半。

### 3.5 接线与模态互斥

- `src/lib/modals.ts` 新增 `resolveModalAction(active, requested)` 三分支（`open` / `close` / `ignore`）；`App.tsx` 原 6 个模态布尔量收敛为单个 `activeModal`，`requestModal` 是**唯一**归并点。两处行为变化属修正：过去「设置打开时按 `mod+/`」会叠加两个面板，现在被忽略；同一快捷键重按统一为关闭。
- **模态层提到 `modalLayer` 并在两个分支都渲染**（评审 P2-2）：禅模式分支此前不渲染模态而 `requestModal` 仍置位 → 全局静默锁（`mod+p` 无反馈，随后的 `mod+shift+f` 被 `ignore` 吞掉）。顺带把 `ConflictDialog` 一并纳入该层——「不可渲染的模态 = 静默故障」对它同样成立（阻塞式确认弹不出来等于保存被无声卡住）。
- **快捷键 `quickOpen` 默认 `mod+p`**，参与自定义与冲突检测，`ShortcutsHelp` 补描述项。计划书的备选方案 `mod+shift+p` 同样被占用（备选键无效），溯源为 CM `defaultKeymap` 内嵌 emacsStyleKeymap 的 `{key:"Ctrl-p", run:cursorLineUp}`；项目**早已为同源的 Ctrl-n（cursorLineDown）做过同样过滤**，故按既有先例一并过滤。代价：源码模式下 emacs 风格 `Ctrl-p` 不再生效（`shortcuts.test.ts` 断言锁定，防将来 CM 升级漂移）。
- **Esc 层级**：`activeModal` 在 App 内（非 store），按 `useGlobalShortcuts` 既有模式新增 `GlobalShortcutHandlers.isModalOpen`，模态打开时让位给模态自己的 Esc 监听（已核对六个模态都有 Esc 监听，不会变死键）；E2E Q10 验证两次 Esc 的层级。

### 3.6 性能实测（#228 两条验收口径）

测量环境：Windows 本机、warm cache、5 轮取中位数；合成工作区为 `dNNN/fNNNN.md`。

| 组成项 | 结果 | 说明 |
|---|---|---|
| Rust 遍历 5,000 文件（索引构建） | **中位数 20.3 ms**（18.9 / 24.4） | 验收线「< 2s」，约 **100× 裕量**；同基准 50,000 文件 154.9 ms，线性 |
| 打分排序 5,000 候选 | **中位数 1.8 ms**（1.5 / 4.9） | 纯函数，即按键真正触发的那一段 |
| 打字是否触发磁盘 / 索引工作 | **否**（确定性断言） | 索引命中缓存；单文件模式根本不发命令 |
| 渲染行数上界 | **≤ 200**（确定性断言） | 5,000 候选下已验证，输入过滤后同样受约束 |
| DOM 渲染耗时 | **无法在 harness 中有效量化** | happy-dom 下 13 行 0.09ms vs 200 行约 65ms，随行数陡增——该环境不是 DOM 计时的有效仪器，故**不以此充当真机数字** |

**边界结论**：单次按键的**必然**成本 = 对已建好的候选集重新排序（1.8ms）+ 渲染 ≤200 行，与工作区文件总数无关，因此「首字符到结果渲染 < 50ms」在**结构上**不依赖机器快慢；但真实浏览器 / 真机的 DOM+绘制耗时没有有效的自动化手段量化，按计划 §7.6 该数字属**人工核对**项，**不写成「已验证达标」**。

## 4. #243：索引遍历的符号链接用例（闭合 #222 计划 §7.1 第 3 项）

#222 计划的 §7.1 列了 15 项行为清单，逐项对账后只有第 3 项「目录符号链接不被跟随（不成环）」没有对应断言。行为本身是对的（`ignore` crate 的 `follow_links` 默认 `false`，且目录链接会落到 `!is_file` 分支 `continue`），但**没有测试锁定**——将来谁把 `follow_links` 打开都不会有测试变红。

单文件 `src-tauri/src/commands/ignore_rules.rs`（+84 行，全是测试）：

| 用例 | 覆盖 |
|---|---|
| `directory_symlinks_are_not_followed` | 同时建「指向真实目录的链接」与**自指链接**；断言链接里的内容不进结果、且遍历能正常结束（自指链接若被跟随就是无限递归）。Unix 用 `std::os::unix::fs::symlink`，Windows 用 `mklink /J` 目录联接（不需要管理员 / 开发者模式） |
| `file_symlinks_are_treated_as_files` | 锁定「只跳过**目录**链接、文件链接按文件处理」这条既有语义（对应 `is_symlink()` → `metadata().is_file()` 分支） |

**环境守卫的口径订正**：评审指出原叙述把单一环境的表现当成了通用语义。独立复测结论是**两种表现都真实存在、取决于进程环境**——评审侧探针得到 `Err(Os { code: 1314 })`（特权不足），本机 `cargo test` 进程内得到 `Ok(())` 但 `link.exists() = false`（返回成功却没建出链接）。因此跳过判据落在「链接确实可用」（`!created || !exists()`），注释改为「返回值不可靠：两种表现都实测到」，不宣称任何单一机制。

## 5. 测试与验证
